A daily process an AI can't quietly skip

I run my job search through an AI assistant. In September I found it had been skipping whole steps for more than a week and reporting them done. This is the system I built so that can't happen again.

What went wrong

The search has a fixed daily routine: a set of searches across job boards, a pass through my inbox, and a tailored application for each role I choose. I gave an AI assistant written instructions and let it run the routine in conversation.

It reported every day as complete. When I checked one day's work against the instructions, it had run 2 of the 11 required searches. The instructions were clear. Nothing enforced them.

My first fix was a checklist script. A review of that script found two problems: it had never been run, and it would mark a step done with no proof that anything had happened.

How it works now

The routine runs in six steps. Three of them are stops, where a script or a person has to pass the work before it moves on.

  1. PlanA data file lists every search the day requires. A script reads it and prints the plan.
  2. Run and recordEach search is logged with the address that was loaded and the first three results.
  3. VerifyOne command fails if any required search is missing. No report is written until it passes.
  4. BuildFor each role I pick, the assistant builds a resume from one master file.
  5. GateA script checks every document and requires a saved copy of the posting.
  6. SendI read each package and submit it myself.

A stop. Work does not pass without a check.

Four decisions

Rules live in data, not in instructions
The assistant and the checker read the same file, so there is one definition of the day's work. On November 13 I retargeted the whole search by editing that file. The daily set went from 23 searches to 18, and the checker enforced the new set on the next run.
Every step leaves a file
A search leaves a ledger row. A package leaves a saved posting and a written read-through. The next step looks for the file and stops if it isn't there.
Every rejection is logged with a reason
A posting I turn down gets a row and a reason code. Later runs check new results against that log, so a rejected posting doesn't come back.
A person decides at fixed points
I choose which roles to pursue. I read every package before it goes out. I send every application myself. The assistant works inside those points and has no way around them.

What broke, and what I changed

What brokeWhat I changed
The first full plan would have demanded about 140 searches in one day.Split the work into a required daily set and a slower rotation, each with its own schedule in the data file.
One job board was running 27 searches a day by accident.Replaced them with a single scan of the whole board, sorted by date.
The inbox check only looked at the inbox. I file job mail under a label, so 108 messages were invisible to it.The check now queries the label as well as the inbox.
LinkedIn results were read from page one only, about six postings.Each search now reads four pages, and the ledger records how many results it saw.
One LinkedIn pass returned 1,600 results that were really 698 roles. The rest were reposts and city copies.Added a cutoff that drops postings older than the last run, and a company-and-title check against everything already logged.

Who did what

I built this by directing Claude Code, Anthropic's coding agent. I don't write Python by hand. I set the rules, decided what counts as evidence, and review what comes out. The assistant runs the searches and drafts the documents inside those rules.

The same approach works for any routine an AI runs on a team's behalf: reporting, reconciliation, intake, status collection. Define the work as data, require evidence for each step, and put a person at the points where judgment matters.
